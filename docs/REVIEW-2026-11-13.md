# Golf Scoring Apps — review of data isolation and event preparation

Reviewed 13 November 2026. Published versions examined: Away Golf Scorer 15.97.31 and Golf Event Scorer 0.5.28. Corrections described below are local and unpublished. Database migrations are prepared and tested, not applied to production.

## Assessment

The basic model from event details, through player selection, handicaps, competitions, rules, NTP, review, teams and publication is sound. The apps use separate databases; Event Scorer additionally isolates groups, approvals and organiser workspaces. Event/player identity is based on IDs rather than matching names. Published course snapshots, revision checks and accepted-score receipts protect live events and final results.

The review did find genuine gaps. They are corrected in the working source, with tests, rather than dismissed as cosmetic issues. This is not a claim that software can be proved defect-free or that every device's unsynchronised data has been inspected.

## Findings and corrections

| Finding | Consequence before correction | Prepared correction |
|---|---|---|
| DEMO profiles shared the general selection pool with genuine profiles | A genuine draft could accidentally receive a copied DEMO player; copied names made this hard to notice | Pools and named-list editing respect DEMO batches. Mixed rosters and unclassified DEMO rosters are rejected at review, event completion, initial publication and update. Synthetic master profiles have an organiser-facing DEMO label. |
| Switching a populated draft to the DEMO list retained unrelated assignments | Old genuine-player handicap maps, shared positions or teams could remain in the draft | A confirmed switch removes those draft-only assignments. A published genuine event cannot be converted to a DEMO event. The DEMO marker does not turn on the older local-test validation bypass. |
| Test handicap calculations could update genuine master profiles | Invented test GAs could become the golfer's saved GA | Automatic GA write-back skips genuine profiles for recognised test/demonstration events. Genuine events still save genuine GAs normally. |
| Test-history exclusions depended too heavily on the event name beginning with TEST | Renamed tests, DEMO batches and demonstration groups could affect normal history | Client classification recognises explicit flags, batch membership, TEST/DEMO/DEMONSTRATION names and the active test group. Prepared server migrations independently classify completed history. Scorer's annual selection rechecks the source event/group, including older snapshots claiming test=false. |
| History cleanup treated a sign-off timestamp as evidence that counters had been incremented | Cleanup could subtract genuine group/partner history, or subtract twice through duplicate workspace copies | Subtraction requires an event-specific recorded-history receipt, consumes it once, and changes 4BBB partner counters only for a 4BBB day. Ambiguous legacy counters are preserved rather than guessed. |
| DEMO batch deletion removed history using individual IDs, although counter keys are player pairs | Batch-related counter entries could remain | Deletion now matches both IDs in pair keys and removes DEMO-only deleted-profile remnants. Unrelated histories remain. |
| Away's service-worker cache label was still 15.97.27 while the release files were 15.97.31 | Cache installation/update behaviour could be inconsistent | The source cache label is aligned with its release. A future publication must advance versioned assets and the cache together. |
| Publication/update requests could outlive the event open on screen; Scorer lacked Away's repeated-publication guard | An old response could attach to a different open event; repeated clicks could overlap | Publication uses a saved identity, captures its payload, blocks overlap and checks the active event. Update reads/responses are rejected after an event switch. Scorer now uses the corresponding publication safeguards. |
| Final locking did not reuse every Final Check condition | Some invalid saved states could reach the final control despite a visible warning | Final locking now also requires the shared Final Check to pass, including roster, course-card and handicap checks. |
| Several verification fixtures still described superseded behaviour | Real test failures were obscured by obsolete assertions and missing fixture dependencies | Fixtures now exercise current behaviour, including authorised phone deletion, visible incomplete checks, current NTP helpers and protected played teams. Shared code pins were refreshed only after exact cross-app comparisons. |

## Home through publication

| Stage | Reasoning and protection examined |
|---|---|
| Home / workspace | New, saved and published events retain separate identities. Scorer starts in an approved group with group-scoped storage and server authorisation. Test fixtures do not become Scorer's initial member database. |
| Event details | Per-day dates, courses, start method, start holes, times and intervals feed the same day model. The seven-day test covers rest days, Vietnam time and legacy one/two-day events. |
| Players | Invitation/acceptance status and daily availability determine the field. Shared positions resolve the actual golfer for the day. Substitution candidates and DEMO batches retain ID boundaries. Duplicate-name labels do not merge profiles. |
| Handicaps | Missing non-GolfLink estimates and both categories are checked. GA, tee handicap and team handicap remain different values. Sorting does not discard entered values. Test GAs are excluded from genuine profile write-back. |
| Competitions and rules | Daily schedules and scoring-method compatibility are checked. Ambrose settings, drive requirements, selected-player eligibility and putting rules feed the event rules. Short-team text follows the competitions actually selected. |
| NTP | Selected course/day holes drive previews and printing. Event-name headings, small movable-marker tags and scorecard-sized distance sheets are covered. |
| Review and teams | Wizard and Teams use shared Final Check logic. Missing categories/players/tees remain visible. Rebuilds retain the selected method; GA balancing includes the assigned virtual player for non-Ambrose short teams. Ambrose three-player balancing remains proportional. Saved or played groups are protected. |
| Preview / final update | Preview is distinct from final locking. Final preparation requires saved teams and complete checks; pending invitations block the final update. Server validation checks membership, course approval, revisions and published settings. Course snapshots protect a published event from later master changes. |
| Scoring / results | Existing acceptance and archive tests verify separate scorer/marker submissions, durable offline copies, revision-aware retries, incomplete-card blocking, final sign-off and immutable awarded history. These remain part of the review because publication must lead to a coherent scoring record. |

## Read-only production observations

No live player, event, course, score or award was edited for this review.

- All public tables checked have row-level security enabled: 13 in Away and 9 in Scorer.
- Scorer: 0 events detached from a group; 0 players detached from a group; 0 cross-group references among saved confirmed-player IDs.
- Scorer: 0 finished events with a TEST/DEMO/DEMONSTRATION name and a missing/false retained test flag.
- Away: 0 published payloads containing tagged DEMO players, and consequently 0 mixed tagged-DEMO/genuine published rosters in that query.
- These aggregate checks do not recognise invented GolfLink numbers as synthetic, do not inspect every historical name/record as a human would, and do not inspect unsynchronised PC/phone/tablet storage.
- Database advisories were also read. Anonymous/player access and security-definer RPC notices largely describe the intended token/organiser API. Schema placement of extensions and leaked-password settings remain maintenance items; the audit did not change production authentication or claim a penetration test.

## Important boundaries for Oatlands training

Use a separate Scorer demonstration/test group, with its own player profiles, and name the training event clearly as DEMO or TEST. Invented GolfLink numbers have the same shape as real numbers, so no app can reliably recognise them from the digits alone. Do not enter those profiles into a genuine customer group and expect the numbers themselves to isolate them.

The shared master course catalogue is deliberately genuine data used by both apps. Selecting Oatlands for a demonstration is safe; saving fabricated ratings or hole data into the master editor is a genuine catalogue change. Event layout overlays and published course snapshots have their own scope and do not silently rewrite the master.

The built-in DEMO list intentionally copies player names where requested, but creates distinct player IDs and synthetic handicaps, omits real contact/GolfLink details and carries an explicit batch marker. It does not identify a golfer by name alone.

## What remains before release

1. Deploy each app's prepared `demo_data_isolation` migration to its matching database, then publish the reviewed frontend/build with newly coordinated release versions and cache labels. Neither step was performed in this review.
2. Run a short real two-phone demonstration after publication: preview, final update, join, score/marker agreement, interrupted connection and reload. Automated tests cannot establish Android sleep/radio behaviour.
3. If historical local counters are suspected of already containing tests, inspect the actual device backup before repairing them. Counters without contribution receipts cannot be safely reconstructed by subtracting inferred events. No broad reset or retroactive change to awarded results was made.

Historical migrations and dated repair notes remain as provenance, not instructions to rerun seed data or recalculate old prizes. Disabled automatic course replacements remain disabled. Historical public GitHub revisions were not rewritten.

## Verification

Final automated results and scope are recorded in `REVIEW-2026-11-13-EVIDENCE.json`. The tests use synthetic fixtures and isolated local PostgreSQL/PGlite databases. They include build provenance, generated Scorer source, shared-function parity, roster isolation, genuine-GA preservation, history cleanup, publication switching, annual server rejection and existing acceptance/retention matrices.

No browser visual pass or physical multi-phone field test was completed in this audit. A successful build/test run is evidence for the tested paths, not proof of a defect-free live service.
